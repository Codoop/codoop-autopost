# 项目初始化与内容工作流设计

[English](./project-initialization-optimization-plan.md) · **简体中文**

状态：已在 `0.0.1-alpha.3` 实现。

## 目的

在发现或生产内容之前，先为一个内容运营工作区确定标准。此后，插件把热点发现和内容生产分成两条独立流程：

```text
初始化运营标准
  → 发现并审核线索
  → 保存值得核验的未验证线索
  → 领取一条未使用线索
  → 核验、写作、批准和发布
```

这样，发现流程可以一次留下多个有价值的机会，而不必为每个候选都创建内容工单。

## Skill 结构

```text
codoop-autopost
├── codoop-autopost-init
├── codoop-content-discovery
├── codoop-content-ticket
└── 内置辅助 Skill
```

- `codoop-autopost-init`：确认项目章程和表达规范。
- `codoop-content-discovery`：运行 `last30days`，审核所有新候选，只保存值得核验的线索。
- `codoop-content-ticket`：领取一条未使用线索，执行以证据为先的内容生产流程。
- 内置辅助 Skill：负责访谈、发现、来源读取、编辑和通过 X 官方 API 发布。

缺少 `PROJECT.md` 或 `VOICE.md` 时，发现与生产流程都必须拒绝运行。

## 初始化边界

初始化 Skill 会：

1. 使用 `grilling`，每次只问一个问题。
2. 在写入前确认 `PROJECT.md`。
3. 在写入前确认 `VOICE.md`。
4. 仅在缺失时创建私有 `config.toml` 模板。
5. 确保 `content-leads/` 与 `content-tickets/` 存在。

它不会发现热点、创建工单、核验来源，也不会要求用户把密钥粘贴到对话中。已有配置值必须保持不变。

以后修改项目定位或表达风格时也使用同一个 Skill：定位变化时重新确认 `PROJECT.md`；只改语气时重新确认 `VOICE.md`。

## `PROJECT.md` 约定

`PROJECT.md` 回答项目写什么、写给谁以及不写什么：

```md
# 项目章程

## 赛道定义
## 主读者
## 内容支柱
## 发现方向
## 全局禁区
```

- 只定义一个明确赛道，不能只写“AI”或“科技”这类宽泛标签。
- 只定义一个主读者，记录身份与场景、当前目标和已有基础。
- 维护三到五个长期内容支柱，并明确包含与排除范围。
- 维护三到五个与内容支柱对应、可重复使用的发现方向。
- 记录跨支柱的硬边界，例如无关蹭热点、未经证实的传闻、攻击个人或用户明确排除的风险。

平台凭据、表达规则、每日选题、SEO 关键词库和项目级来源白名单不应写入 `PROJECT.md`。

## `VOICE.md` 约定

`VOICE.md` 回答这个项目应该怎样说话：

```md
# 表达规范

## 使用语言
## 读者距离与整体语气
## 句式与节奏
## 格式与符号
## 偏好表达
## 禁用表达
## 已确认的风格规律
```

用户可以选择提供历史文本作为样本。Skill 只从中提取可以检查的规则，不复制样本中的原句、事实或立场。“专业”“有趣”等标签过于模糊，必须转化成能够检查草稿的具体规则。

## 工作区结构

```text
content-operations/
├── config.toml
├── PROJECT.md
├── VOICE.md
├── content-leads/
│   ├── available/
│   ├── claimed/
│   ├── consumed/
│   ├── rejected/
│   └── runs/
└── content-tickets/
```

`content-leads/` 是永久保留的本地未验证线索队列和发现报告。`content-tickets/` 保存已领取线索的证据、文案、审核、排程、发布回执和可选表现数据。

工作流使用本地文件和原子目录移动，不需要数据库、后台服务、隐藏状态或由 Git 驱动的状态机。

## 两条工作流的交接

### 热点发现

每次发现运行会选择一个项目发现方向，保存原始 `last30days` 结果，并让一个全新的审核 subagent 评估所有新候选。审核者使用固定保存、未经修改的上游 Marketing `Twitter Engager` 角色，再补充当前项目背景和本次任务说明。

审核者不能打开候选链接，也不能把发现摘要当作事实。普通候选只有获得 `go` 才进入 `content-leads/available`；`weak` 和 `reject` 永久保留在本次发现报告中。数据明确显示热度异常爆发时，可以使用受限的 `breakout-trend` 通过依据；人工也可以填写理由，明确提升一个已审核候选。

### 内容生产

生产流程会先恢复未完成的已领取工作；否则自动从最新一轮发现中领取排名最高且未过时的线索。同一条线索不能被领取两次。

工单随后依次执行重复检查、通过 Firecrawl 核验一手来源、全新的核验后价值审核、写作、人工明确批准，以及通过 X 官方 API 发布。没有合适线索时，生产流程会停止并提示重新运行发现；它不会自动启动发现。

## 不可绕过的安全规则

- 发现数据只是线索，不是事实证据。
- 线索未领取或重复检查未通过时，不能调用 Firecrawl。
- 没有保存一手来源快照、明确的已验证证据和第二次审核的 `go`，不能开始写作。
- `breakout-trend` 和人工提升只换取核验机会，不能绕过后续门禁。
- 发布必须获得人工明确批准，并显式执行真实发布命令。
- 禁止浏览器发布以及自动回复、点赞、关注或私信。
- 成功发布的线索会被消耗，不能再创建另一张工单。
- 发布失败时保留工单、回执和已领取线索，供人工恢复。

## 当前范围

当前生产流程每条线索只生成一条不超过 280 字符的 X 帖子。多平台生产暂不实现；未来可以继续复用同一个线索池和证据流程，而不必修改热点发现流程。
