# 运营项目初始化与内容工单优化方案

状态：第一版已实现。

## 目标

把插件拆成“先定义运营标准，再运行内容工单”的两层工作流。用户只安装一个 `codoop-autopost` 插件；每个运营项目只服务一个垂直赛道，后续的热点筛选、来源核验、草稿、审核与发布都必须遵守该项目已确认的标准。

## 插件内的 Skill

```text
codoop-autopost 插件
├── codoop-autopost-init
├── codoop-content-ticket
└── grilling
```

- `codoop-autopost-init`：初始化或更新运营项目。调用 `grilling` 与用户逐题沟通，分别产出并确认 `PROJECT.md`、`VOICE.md`。
- `codoop-content-ticket`：创建和推进一张内容工单。它不发起定位访谈，只读取已确认的项目标准。
- `grilling`：原名内置，不要求用户另行安装。保留其原有名称与 MIT 归属。

`codoop-content-ticket` 发现 `PROJECT.md` 或 `VOICE.md` 缺失时，必须拒绝创建、修改、排程或发布工单，并提示用户先运行 `codoop-autopost-init`。

## 运营项目目录

```text
content-operations/
├── config.toml
├── PROJECT.md
├── VOICE.md
└── content-tickets/
    └── C-YYYYMMDD-<slug>/
        ├── ticket.toml
        ├── discovery/
        │   ├── raw.json
        │   ├── candidates.md
        │   └── selection.md
        ├── verification/
        │   ├── evidence.md
        │   ├── claims.md
        │   └── source-snapshots/
        ├── writing/
        │   ├── brief.md
        │   ├── drafts.md
        │   └── edited.md
        ├── review/
        │   ├── final.md
        │   └── approval.md
        └── publish/
            ├── schedule.toml
            └── receipt.json
```

- `config.toml`：已启用的平台、凭据、API 地址和运行参数。第一版只启用 X；凭据不进入项目标准或工单。
- `PROJECT.md`：赛道与内容边界。
- `VOICE.md`：语言和表达规则。
- `content-tickets/`：跨平台的内容工单目录；`C-` 表示 Content，不绑定 X 或单条帖子。
- 所有内容工单直接读取根目录的 `PROJECT.md` 与 `VOICE.md`；不保存副本或版本快照。

## 初始化流程

初始化不要求 Firecrawl 或 X 凭据。用户可先完成定位和语气，再在需要核验或发布时填写 `config.toml`。

1. 用户显式运行 `codoop-autopost-init`。
2. Skill 使用 `grilling` 一次只提出一个问题；每题先给推荐答案、理由和例子，用户确认、修改或否决后才进入下一题。
3. 先完成 `PROJECT.md` 的访谈和显式确认。
4. 再基于已确认的项目定位，完成 `VOICE.md` 的访谈和显式确认。
5. 两份文件都确认后，初始化 Skill 才宣布项目可以创建内容工单。

不保存访谈草案。用户未明确确认前，Agent 不得写入正式 `PROJECT.md` 或 `VOICE.md`，也不得将访谈中的推测当作工单标准。

以后修改赛道或语气时，也使用 `codoop-autopost-init` 与 `grilling`：只改赛道则只重新确认 `PROJECT.md`；只改语气则只重新确认 `VOICE.md`。

## `PROJECT.md` 规范

`PROJECT.md` 回答“写什么、写给谁、不写什么”。第一版不要求内容承诺、商业目标、编辑立场或项目级来源清单。

```md
# 项目章程

## 赛道定义

- 一句话定义：
- 解释：
- 候选内容的相关性判断原则：

## 主读者

- 身份与场景：
- 当前目标：
- 已有基础：

## 内容支柱

### <支柱名称>

- 包含什么：
- 不包含什么：

## 全局禁区

- 永远不做的主题：
- 不做的内容方式：
- 不碰的风险类别：
- 不做的蹭热点内容：
```

### 赛道定义

项目只有一个垂直赛道。赛道必须足够具体，能帮助 Agent 判断候选热点是否相关；不能使用“科技”“AI”“商业”这类过宽标签。

### 主读者

只定义一个主读者画像，并且只记录三项：

- 身份与场景：读者是谁、在何种工作或生活情境中接触内容。
- 当前目标：读者希望解决什么问题、作什么判断或获得什么结果。
- 已有基础：默认已经理解什么、哪些概念仍要解释。

不收集年龄、收入、地域等与内容判断无关的细碎人设。可以存在次要读者，但每篇内容始终优先服务主读者。

### 内容支柱

维护 3–5 个长期内容支柱。每个支柱只记录“名称、包含什么、不包含什么”，不预建选题库或 SEO 关键词库。

每个热点候选都必须归入一个支柱；无法归类的内容不能进入工单。看似相关但落入支柱“不包含什么”的内容也必须淘汰。

### 全局禁区

全局禁区是跨支柱的硬边界，例如与赛道无关的蹭热点、未经证实的传闻、攻击个人，或用户明确排除的高风险话题。命中任一禁区时，Agent 直接停止该候选，不进入写作、审核或发布。

### 不放入 `PROJECT.md` 的内容

- 平台、凭据和 API 参数：放入 `config.toml`。
- 语言、语气和句式：放入 `VOICE.md`。
- 关键事实的一手来源要求：插件的全局安全规则；项目只能加严，不能放宽。
- `SOURCES.md`：第一版不创建。

## `VOICE.md` 规范

`VOICE.md` 回答“同一个项目应该怎样说话”。它不定义赛道，不替代事实核验，也不保存用户提供的原始样本。

```md
# 表达规范

## 使用语言

- 主要语言：
- 英文术语策略：

## 读者距离与整体语气

- 与读者的关系：
- 希望呈现的语气：
- 不应呈现的感觉：

## 句式与节奏

- 句子长度偏好：
- 开头偏好：
- 常用展开结构：
- 第一人称和第二人称规则：
- 段落与线程拆分习惯：

## 格式与符号

- 列表、编号和标题：
- Emoji、括号、破折号、引号和感叹号：
- 链接、引用和 CTA：

## 偏好表达

- 常用开场、转折和结论方式：
- 希望多用的词语或表达特征：

## 禁用表达

- 禁用话术、词汇、句式和格式：

## 已确认的风格规律

- 可执行的抽象规则：
```

用户可以提供历史帖子或其他文本作为风格样本，但这不是强制项。Agent 只从样本中抽象可执行规律，例如“先给结论再解释”“每段最多两句”“避免感叹号”；不把样本文字、事实或立场复制进 `VOICE.md`。

“专业”“有趣”“有温度”等抽象标签不能作为最终结论。Agent 必须继续追问，直到形成可在草稿中检查的具体规则。

## 内容工单流程

一张内容工单只产出一个最终内容单元。第一版为一条 X 帖子或一个线程；`discovery/` 可以保存多个候选热点，但 `selection.md` 只能选择一个方向。

工单必须在热点发现之前创建。这样候选、筛选、证据、写作、审核和发布结果从一开始就保存在同一个 `C-...` 目录内。

工单状态保持：

```text
draft -> pending -> done
```

- `draft`：发现热点、核验来源、写作和编辑。
- `pending`：完成最终稿、通过标准检查，等待用户审核或已获批准并排程。
- `done`：发布成功，回执写入 `publish/receipt.json`。

失败时保留 `pending` 状态与失败回执，不自动重试。

### 两个标准检查点

`codoop-content-ticket` 只在两个节点检查根目录的 `PROJECT.md` 与 `VOICE.md`：

1. 热点筛选完成后：检查候选是否符合主读者和内容支柱，且未命中全局禁区。
2. 最终稿进入人工审核前：再次检查赛道边界、事实证据与表达规则。

两次检查都通过，工单才可以进入 `pending`。这不替代用户的最终批准；发布仍需用户明确批准以及 `--live`。

## 全局安全规则

- 热点发现只用于发现讨论，不可作为事实来源。
- 关键事实必须尽量追溯官方公告、原始报道、论文或当事人原帖。
- 每条关键主张保留 URL、来源类型、发布日期和原文摘录。
- 证据不足、来源冲突或无法确认的主张不得进入最终稿。
- 明确区分可验证事实、他人观点与作者分析。
- 第一版只使用 X 官方 API 发布；禁止浏览器自动化和自动互动。

## 实现边界

本方案不引入数据库、后台服务、访谈草案文件、项目级来源白名单、选题库或 SEO 关键词库。先用 Markdown 文件、现有文件工单和内置 Skill 完成闭环；复杂能力在出现真实需求后再增加。
